# CONTAINER REPORT — 34-slice CascadeContainer for the K=2400 cascade

Date: 2026-09-15 (session 8, agent H). Local PyEVM only; **0 transactions sent to any chain**.

## What was built

- CascadeContainer.sol — generated by gen_cascade_container.py from
  out/slices2400/cascade_slice_*.json, not hand-written. Takes the 102-bit context,
  runs the 34 burned slices in order, feeds each slice the intermediate wires it needs,
  and returns the 13 output bits.
- cascade_container_wiring_chunks.json — the per-slice wiring (prims/prevs/outs),
  delivered one slice at a time via setWiring(i, bytes) after a small deployment.

**Why not one constructor blob like g44:** the 34-slice wiring is 893,051 bytes. Passing
it as a constructor argument makes the creation initcode 912,172 bytes, which trips the
EIP-3860 initcode limit (49,152) and would fail on any post-Shanghai chain. Storing it
in per-slice chunks keeps every transaction small (max chunk 35,514 bytes) and is still
fully script-generated.

## Verification

Fresh PyEVM chain, official TapeOut CPU deployed, all 34 slices taped out there, container
deployed, wiring set. Results in cascade_container_test.json:

| check | result |
|---|---|
| PyEVM container vs single netlist, 5 sample contexts (2 table entries + 2 held-out + 1 random) | **0 mismatches** |
| exact container logic vs single netlist, all 14,281 table entries + 6,000 held-out (3,000 near + 3,000 far) | **0 mismatches** |

The 20,281-context check is done by a numpy reimplementation of the same wiring (PyEVM is
~1M gas/s, so thousands of on-chain-style runs would take days); the 5-context PyEVM check
establishes the deployed container equals that logic. Zero is the only acceptable answer
and it is zero.

## Gas and the g44 gap

Measured on the local PyEVM CPU (receipt gasUsed, not a model):

| quantity | value |
|---|---|
| container run gas (measured) | **856,696,224** |
| pure gate cost model (34 x 52,667 + 150,895 x 2,258.8) | 342,632,304 |
| **overhead** | **514,063,920 = 2.50x the pure cost** |
| per-token blocks (gas / 70,000,000) | **12.24 blocks/token** |

The g44 gap reappears and is worse at this scale: g44 measured 72,655,025 against a pure
44,461,275 (1.63x, 28.2M overhead); the cascade is 2.50x. The overhead is dominated by the
container's own marshalling, not the CPU step: reading 893 KB of wiring from storage
(~27,900 SLOADs), 159,626 input-side and 137,907 output-side bit gathers/scatters in
Solidity, and the 18,530-byte buffer's memory expansion. At 34 slices the marshalling is
the same order of magnitude as the gate evaluation itself.

## Wiring shape

| quantity | value |
|---|---|
| slices | 34 |
| records burned (incl. last_outs buffers) | 150,895 |
| single-netlist NAND | 148,235 |
| wiring bytes | 893,051 |
| unique crossing wires | 137,907 |
| crossing references (total intermediate wires carried) | 159,626 |
| **widest single crossing** | **7,442** (slice 25) |
| max wiring chunk | 35,514 bytes |

Per-slice guards (permanent, in the generator): slice 0 carries the full 102-bit context;
every later slice consumes at least one intermediate wire; every slice produces at least
one wire; every consumed intermediate wire was produced by an earlier slice. A silent
zero-feed between slices now fails the generator, the same way the keygen check fails the
table build.

## Mainnet feasibility read

- The container run is **856.7M gas, ~12.2 blocks**, far over the 70M block gas limit. A
  transaction cannot run it; an eth_call is not bound by the block limit. Your 140M/400M
  eth_call checks are confirmed in principle, but **this run needs ~857M gas**, beyond the
  400M you verified, so the demo node must be confirmed to accept an ~860M-gas eth_call.
- Deployment is a separate, larger cost and is NOT part of this task: 34 slice tape-outs
  (447.5M estimateGas total, already measured) + 1 container deploy + 34 setWiring txs
  (~558M storage gas total), roughly 1.0B gas across ~69 transactions.
- **Latency:** I cannot measure mainnet latency because nothing is deployed on mainnet and
  this task sends nothing. Local PyEVM is ~5 minutes per run and is not representative.
  As a planning number for the page: 857M gas on a typical full node at ~10-30M gas/s of
  compute-heavy execution is roughly **30-90 seconds per call**, to be measured live after
  the user burns the slices and deploys the container. Visitors will feel that; it is not
  interactive.
